SPSync record data support plan
===============================

Markers as in dev-phases.txt:  + done   * in progress   - todo
Written 2026-08-30, decisions RD11-RD13 and the resolved questions added 2026-09-07
(after distributed phase 4 / M3). Cross-references: use_cases.txt (1: file-like
sync on mobile), progress_indication.txt, segments.txt (S6 retention),
distributed_sync.txt (D1 content-blind servers, phase 4 s2s), data_changes.txt,
dev-phases.txt phase 2.


Purpose
-------

Records today carry only metadata; the actual payload ("record data") of an object
change - a file, an attachment, any biggish blob - has an interface
(core/record_data.hpp), a state machine, protocol stubs (request_data/response_data,
server replies not_implemented) and a data_change_info field, but no implementation
anywhere. This plan makes record data real, sized for file sync / file transfer:
multi-gigabyte objects, resumable transfers, lazy per-object fetching on mobile
(use case 1), verifiable end to end while the server stays content-blind (D1).

Data is deliberately NOT part of the record chain: the record authenticates a
descriptor of the data, the bytes travel and are stored out of band. Committing a
record never waits for its data upload; readers see the record immediately and the
data state separately (record_data_state::remote_not_complete exists for this).


Current state (2026-08-30)
--------------------------

Exists:
  - core/record_data.hpp: record_data interface (offset read/write, remove_data)
    and record_data_state {deferred, remote_not_complete, upload_pending,
    download_pending, in_sync, removed, invalid} - the states already match the
    flow below.
  - data_change_header: optional data_change_info{size, iv, gcm_tag} inside the
    ENCRYPTED header - designed for one GCM pass over the whole blob (64 GiB cap,
    no random access, server cannot verify anything). Superseded by RD2/RD3.
  - protocol: request_data{record seq, start, end} / empty response_data; server
    connection replies not_implemented; comm::handle(response_data) stub.
  - record_objects.data_ref column in the client record storage, never set.
  - crypto: auth_stream_cipher (streaming AES-GCM with AAD), sha3, PQ signing.
  - engine: sync_object_change(oid, metadata, record_data_handle = {}) already
    accepts a data handle and drops it.

Missing: everything behind those seams - no data store on either side, no chunking,
no upload/download, no verification, no lifecycle.


Design decisions
----------------

RD1 Separation of record and data. The record chain stays small and fast to sync.
    A single_change may reference one data blob through a descriptor that is part
    of the authenticated record; the blob itself is chunked, stored and moved
    independently. Record commit never blocks on data (mobile, resume, "message
    before attachment"); consumers must tolerate remote_not_complete.

RD2 Descriptor, two views (replaces data_change_info):
      plain part of single_change (server-visible, authenticated):
        enc_size          total encrypted size (quota checks, progress)
        chunk_size        chunking used for this data
        manifest_digest   sha3-512 over the ordered list of chunk digests
      encrypted header (members only):
        plain_size        plaintext size
        content_digest    sha3-512 of the plaintext (end-to-end integrity, later
                          dedup basis)
    The server-visible half leaks only sizes (which traffic reveals anyway) and
    lets the server fully verify stored bytes without decrypting: the client sends
    the chunk digest list (manifest) first, the server checks it against
    manifest_digest, then checks every chunk against the manifest. Junk uploads
    and bit rot die at the server's edge; s2s replication gets the same check for
    free. data_id := manifest_digest (stable across rebases, see RD7).

RD3 Chunked encryption. Chunks of chunk_size (default 1 MiB, per-storage config)
    encrypted independently:
      data_key   derived per data from the group encryption key and a random
                 per-data nonce (HKDF over sha3); key separation means GCM nonce
                 management is local to one data
      nonce      chunk counter
      AAD        data nonce + chunk number (no reorder/transplant)
      per chunk  AES-256-GCM tag stored with the chunk
    The per-data nonce and encryption key sequence live in the encrypted header.
    Chunking removes the old 64 GiB single-GCM cap and gives random access:
    reading offset X decrypts only the chunks covering X; a failed chunk marks the
    data invalid, not the record.

RD4 Transfer protocol (flesh out the c2s stubs; all inside the encrypted
    transport as today):
      upload_data_manifest {tag, change idx, chunk digests}   opens an upload,
          server verifies against the committed record's manifest_digest;
          response says which chunks it already has (resume)
      upload_data_chunk {data_id, chunk no, bytes}            server verifies the
          digest, stores, acks with a window to keep pipelining
      request_data {tag, change idx, chunk range}             replaces the seq
          based stub; response_data streams the chunks it has and states
          completeness
      notify_data {sid, tag, change idx, complete}            to storage listeners
          when a data becomes complete, so waiting clients fetch without polling
    Uploads happen after the record is acked (the tag exists server side);
    interrupted transfers resume by manifest. Fetch is pull-based and lazy by
    default (use case 1: fetch data for individual files only).

RD5 Server data store. Chunks as files under the storage directory
    (record-storages/<sid>/data/<data_id>/...), sqlite is for the bookkeeping
    only: data table {data_id, record tag, change idx, enc_size, chunk_size,
    manifest, have-bitmap, complete}. The server never decrypts (D1). Limits and
    quota per RD10; incomplete uploads expire. Chunks of records that are pruned
    at a segment cut are deleted unless a retained record still references the
    same data_id (segments.txt S6).

RD6 Client data store. One record_data implementation over the same chunk-file
    layout plus local state (record_objects.data_ref finally points at a client
    data table row: {data_id, state, have-bitmap}). Policy per storage: lazy
    (deferred until asked - mobile default) or auto-fetch up to a size threshold.
    read() decrypts chunk-wise and verifies on the fly; locally created data is
    written through the store's data_writer before upload (RDS 2: the data_id
    exists only after the last chunk, so a stored record_data is immutable);
    remove_data() evicts local chunks (state removed, refetchable) without
    touching the record.

RD7 Engine flow. sync_object_change with a data handle: stream the source once -
    encrypt chunks into the local store, build the manifest, put the descriptor
    into the record - then commit as usual; comm uploads pending data in the
    background (few in flight, resumable) and flips upload_pending -> in_sync.
    Incoming records with a descriptor surface as deferred/remote_not_complete;
    explicit fetch (or auto policy) drives download_pending -> in_sync. Rebase
    reuses the data untouched: the descriptor is inside the re-signed record and
    data_id/chunks do not depend on the record tag. New engine events:
    on_data_state_changed, on_data_progress (progress_indication.txt wants per
    entity upload/download progress).

RD8 Replication (details belong to distributed_sync.txt): data is not in the
    chain_log and not in the Raft log. Only servers with the data role (RD12) hold
    chunks; they announce availability per data_id (RD13) and replicate chunks
    among themselves by data_id manifest - same verification path as clients -
    according to the copy count of RD13. Record servers never carry bulk bytes.
    Weak and strict mode identical here.

RD9 Lifecycle. A newer change to the same oid supersedes the old data (old one
    becomes prunable at the next segment cut unless retained); remove-type changes
    (the open question in single_change) make the object's data dead. Local
    eviction (RD6) is independent of server retention. Data of records dropped by
    truncate_from (rollback) is dropped with them once no record references the
    data_id.

RD10 Quotas and limits - data AND the record chain. Today the only bound is the
    transport frame cap (16 MiB payload per encrypted frame, framing.hpp): no
    validation cap, record metadata is arbitrary octets, so the chain can be
    bloated as easily as data. Worse, the frame cap plus batching is a wedge
    hazard: response_records packs up to max_returned_records (30) blocks into
    ONE frame, so records above ~max_frame_size/30 (~0.5 MiB) can make a range
    unsendable - each committed fine alone, the batch can never be fetched.
    max_record_size must stay well below max_frame_size/max_returned_records and
    the record batching should become size-aware. Two kinds of limit with
    different rules:

    Validity limits (deterministic, replicated): anything that makes a record
    invalid must be judged identically by every replica, or weak-mode replicas
    diverge and a Raft leader/follower disagree on apply. So max_record_size (and
    the existing max data descriptor bounds) are per-storage creation parameters
    next to storage_modes: wire-encoded in create_storage, persisted in
    storage_config, immutable, checked in chain_sync validation ->
    protocol::errc::record_too_big. Server operator sets the defaults for new
    storages (spsync_server.cfg).

    Resource quota (local, per server): total bytes of stored data, max single
    data size, per-member and total chain growth budgets. These do NOT affect
    record validity - a server may refuse to *accept an upload* or *serve as
    origin* (quota_exceeded, data_too_big) without disagreeing about what a valid
    record is; data completeness already differs per server (RD8), so a peer
    hitting its disk limit degrades availability, not consistency. Enforced at
    the protocol edge: upload_data_manifest/chunk against data quota, commit
    against a chain budget. Accounting is incremental per storage (chain bytes,
    data bytes) in the storage db, recomputed at segment cuts.

    Transfer quota (local, per server): traffic budgets on top of the resource
    quota - bytes uploaded/downloaded per storage (and per member once 2.3 signer
    attribution is wired in) over a time window. Storage quota bounds what is
    kept, transfer quota bounds what is moved: repeated re-downloads of the same
    data cost no storage but real bandwidth, so data serving (request_data) is
    the main consumer. Same nature as the resource quota: server-local,
    accounted incrementally per window in the storage db, refusal
    (quota_exceeded, retry-after) degrades availability only - a client resumes
    in the next window, replication peers (RD8) fall behind but never diverge.
    Chain sync (records) should stay outside the transfer budget or get a
    generous separate one: starving record sync breaks liveness for kilobytes.

    The chain's long-term size control is retention, not quota: history is cut at
    segments (segments.txt S6) and dead data pruned with it; the chain budget
    only guards the growth rate between cuts. Clients learn the limits in the
    storage info exchange (response_sequence_number carries the modes already;
    add the limits) so the engine can refuse oversized changes before committing.
    Per-connection instantaneous rate limiting (bytes/s) is operational
    hardening, phase 7 territory; the transfer quota above is the cumulative
    counterpart.

RD11 Size hiding (2026-09-07). The server must know the ciphertext size and the
    chunk count (it stores, verifies, serves ranges and counts quota) and traffic
    volume reveals the same to anyone on the path (the securepath threat model
    keeps traffic analysis out of scope), so the achievable goal is: the server
    learns a size class, never the plaintext length.
      - Data is padded before chunking, inside the ciphertext, with a size-class
        rule (Padme style: the padded length keeps only a few significant bits;
        overhead capped at ~12% and shrinking with size, floor 4 KiB). Padding
        to chunk_size would turn a 3 KB file into 1 MiB. plain_size in the
        encrypted header is the true length, so readers strip the padding and
        progress stays exact; enc_size is the padded ciphertext size and quota
        counts that.
      - The encrypted record header gets a trailing padding field inside the
        AEAD with the same rule: message texts and inline payloads leak only a
        size class. Cheap, independent of data support, needs the record
        structure version bump.
      - Accepted leaks: chunk count (coarse once padded), the presence of a
        descriptor, access patterns. No dummy data or cover traffic at this
        layer.
    The rest of RD3 stands; the manifest digest in the authenticated record
    already stops a server from truncating or reordering chunks.

RD12 Server roles, data endpoints, tickets (2026-09-07). Bulk bytes never pass
    through a server that will not keep them (servers are traffic bound, traffic
    costs money): no pull-through proxying.
      roles       every server has the record role (chain, commits, s2s heads)
                  and optionally the data role (chunk store). Same binary, same
                  protocol; the data role is its own listener and port so it can
                  sit on another box or link. Deployments: record servers A, B
                  plus data server D; a data server set D1..Dn; or A, B with both
                  roles (the all-in-one replicas of distributed phase 4).
      endpoints   the storage info exchange (the sequence response carries the
                  modes already; add the RD10 limits and the data endpoints)
                  lists the data-role servers of the storage: host, port, key id,
                  optional region label. Cluster configuration on the record
                  servers next to the peer list; the client persists it per
                  storage like the cursor owner.
      direct      clients upload to and download from data servers directly; in
                  the all-in-one setup a client on B wanting data only A holds is
                  told that A has it (redirect, not proxy). Proxying is an
                  explicit fallback for a client that cannot reach any holder,
                  off by default.
      tickets     a data server has no chain, so it can check neither membership
                  nor a manifest against a committed record. The record server
                  issues a signed data_ticket {sid, data_id, manifest_digest,
                  enc_size, chunk_size, member key id, right (upload/download),
                  expiry}; the client presents it, the data server verifies the
                  record server signature (it trusts record server keys the way
                  peers trust each other on hello) and then verifies manifest and
                  chunks exactly as RD4. Quota accounting happens where the ticket
                  is issued. The data server stays blind to content and history;
                  an all-in-one server issues tickets to itself.
      client auth the data listener requires certified client keys (as the
                  packet server does); no shared-secret variant.

RD13 Availability, holder lists, load balancing, copy count (2026-09-07). Two
    pieces of "where is the data", in two places:
      endpoint list   static, RD12 (which servers may hold data of the storage).
      holder list     dynamic: data servers announce availability per data_id
                      (have-bitmap, complete flag, plus load signals: free space,
                      bytes in flight) to the record servers they are configured
                      with, when chunks complete and again in anti-entropy;
                      record servers keep a per-storage availability table and
                      relay it to each other with the heads. The ticket response
                      carries the ordered holder list of the data; the ticket is
                      valid at any holder (it names the data, not the server).
    Holder lists are transient, a fresh ticket always gives the current view; the
    client persists only its own data state and have-bitmap.
    Load balancing is the ordering of that list, decided by the record server
    which issues every ticket anyway:
      downloads   holders ordered by completeness, load, locality; a client may
                  fetch chunk ranges of one data from several holders in parallel
                  (every chunk verifies on its own, the manifest fixes the set).
      uploads     the upload ticket names the preferred data servers in order:
                  round robin / least loaded for ingress, a consistent hash of the
                  data_id for even storage across a set.
      failover    a holder that is down is the next entry; none reachable ->
                  remote_not_complete and a retry with the next ticket.
    Copy count k per storage class instead of eager/on-demand modes: the primary
    holders of a data are the first k servers on the data_id hash ring, data
    servers replicate among themselves until k copies exist, clients download
    from any holder. k = number of data servers is full replication, k = 1 a
    single copy (durability = that disk, no cross-server traffic), k = 2 the
    usual choice. k is server-side policy (operators know the disks), not a
    storage mode; a data server at its quota behaves as if not on the ring for
    new data - availability degrades, nothing diverges. The granularity of the
    balancing is per data and per ticket; finer is the client's chunk-range
    choice. A deployment with one data server degenerates to a list of one.
    Later: surface "held by k replicas" as a data state, the way records
    distinguish acked from in_sync (D8).


Implementation steps
--------------------

+ RDS 1  Descriptor and chunk crypto -- done 2026-09-10                        [1d]
      Descriptor v2 in single_change + encrypted header (RD2), per-data key
      derivation, chunker with manifest build/verify (RD3), size-class padding of
      the data and the trailing padding field of the encrypted record header
      (RD11, structure version bump). Unit tests: round trip, tamper per chunk,
      reorder, wrong manifest, padding classes and stripping, header padding
      invisible to readers. data_change_info retired.
      + core/data/: size_padding (Padme, constexpr; data floor 4 KiB, header
        floor 256 B - "the same rule" of RD11 with a smaller floor so a chat
        message costs ~250 B of chain, not 4 KiB), data_descriptor {enc_size,
        chunk_size, manifest_digest} in plain_single_change_data and data_header
        {plain_size, content_digest, nonce, key_seq, flags} in
        data_change_header, chunk_crypto (HKDF-SHA3-512 data key from group key
        + 16 B nonce, iv = chunk counter, AAD = nonce + counter, tag appended),
        data_manifest (digest, matches(descriptor), verify_chunk),
        data_encryptor (streaming: write() any pieces, chunks to a sink as they
        complete, finish() pads inside the ciphertext and returns descriptor +
        header + manifest) and data_decryptor (any chunk alone, padding
        stripped by plain_size). chunk_count derives from enc_size and
        chunk_size (each chunk carries a tag), nothing extra on the wire.
      + encrypted record headers (all three record kinds) are padded_record_header
        {header, padding} inside the AEAD; record_base::current_structure_version
        = 2, verifiers report supported() and never read another version
        (is_authentic false, headers empty) - old records are not migrated.
      + securepath crypto::hash_stream (incremental sha3) for content and manifest
        digests over streams.
      + tests: core test_record_data_crypto (padding classes, chunk binding,
        round trip incl. 0 bytes and chunk boundaries, tamper/reorder/transplant/
        foreign manifest/wrong key, random access, descriptor serialisation,
        header padding classes), engine creator/verifier (descriptor halves and
        their authentication, padding invisible + size classes, version gate).

+ RDS 2  Client data store -- done 2026-09-18                               [1.5d]
      record_data implementation over chunk files + state table, data_ref wiring
      in record storage, eviction, data_id reference counting. Tests: offset
      read/write across chunk boundaries, remove/refetch state, big-file
      streaming without loading whole blobs.
      + core/data/, four pieces a data server can reuse (RDS 4): have_bitmap
        (one bit per chunk, the persisted/wire octets normalised), chunk_files
        (<root>/<hex data_id>/<chunk no, 8 hex digits>, temp + rename so a chunk
        file is complete or absent; a staging area under <root>/.staging for a
        data whose id is not known before its last chunk, renamed on commit,
        cleared when the store opens), data_state_table (sqlite table
        record_data {key, data_id unique, enc_size, chunk_size, state, have,
        manifest}) and record_data_store on top of them.
      + creating: store.create(group key, chunk size) gives a data_writer -
        write() plaintext in any pieces, chunks are encrypted into the staging
        area as they complete, finish() registers the data as upload_pending
        with everything held and the manifest kept for the upload. The row is
        written before the rename, so a crash leaves an unreferenced row for
        the sweep and never chunk files nothing knows of. This replaces the
        "write() for locally created data" of RD6: a stored data is what its
        descriptor says, record_data::write on it throws.
      + reading: store.open(key candidates, descriptor, header) gives the
        record_data handle; read() at any offset decrypts only the covering
        chunks (the last one is cached, small sequential reads decrypt each
        chunk once), stops at a chunk that is not held, size() is plain_size,
        available_size() the data octets in held chunks (not necessarily
        contiguous). The candidates are the group keys of the header's key_seq
        (D9 collisions); the one that authenticates is found on the first
        chunk. A descriptor contradicting the row of its data_id opens nothing.
      + failed chunk (RD3), two cases told apart by the manifest: a held chunk
        that is no longer the one the manifest names (bit rot, lost file) is
        dropped and the data goes download_pending - refetchable; a chunk the
        manifest names but no key authenticates makes the data invalid. While
        upload_pending (the only copy) both are invalid.
      + transfer side, ciphertext only: set_manifest (must match the
        descriptor), store_chunk (verified against the manifest, so a download
        fetches the manifest first - detail for RDS 6; the last missing chunk
        flips the data to in_sync), read_chunk + manifest for the upload.
      + eviction: evict()/remove_data() drops the chunk files, state removed,
        row and manifest stay so the refetch verifies at once; refused while
        upload_pending.
      + references: record_storage stores the row of the data_id in
        record_objects.data_ref for every change with a descriptor (row created
        as deferred when the data is new - an incoming record - and left alone
        when known); data_ref is no longer unique, old tables are rebuilt on
        open. data_reference_count(local id) counts object rows of records in
        any state, so a rebase (set_record) and truncate_from/truncate_prefix
        move the count with the records; store.remove_unreferenced(predicate)
        sweeps rows + chunks nobody references (RD9) - the engine calls it
        after truncation/rebase, never between a writer's finish() and the
        creation of its record. Servers get the rows as well: the index of the
        data their chain names, which RDS 5 needs for tickets.
      + tests: core test_record_data_store (bitmap, chunk files + staging,
        table persistence, offset reads and pieced writes across chunk
        boundaries, empty data, evict/refetch with tampered and misplaced
        chunks, download into a second store in any order with a gap, key
        candidates, rot vs invalid, writer cleanup, sweep, 24 MiB streamed in
        64 KiB pieces and verified against content_digest) and
        test_record_storage (shared rows, rebase keeps the reference,
        truncation drops it, upgrade of the unique data_ref table).
      Not here: where the client keeps its data directory and the wiring into
      client_sync/engine (RDS 3), a content_digest index for the download skip
      (RDS 3), fsync of chunk files (decide with the server store, RDS 4).

+ RDS 8  Chain validity limits -- done 2026-09-07                          [0.5d]
      max_record_size and chunk_size as per-storage creation parameters (RD10
      validity side, RD3): wire + persistence next to storage_modes, chain_sync
      validation, record_too_big error, limits reported to clients, engine
      pre-check. Size-aware record batching in response_records (fixes the
      frame-cap wedge hazard, RD10). Independent of the data work; wanted before
      distributed phase 4 and now overdue - do it first. Tests: oversized record
      rejected identically on reopen, mismatching creation limits refused, a
      range of large records still fetchable.
      Implemented: storage_limits {max_record_size, chunk_size} inside
      storage_modes (sync_mode.hpp; defaults 256 KiB / 1 MiB, ranges 4 KiB..8 MiB
      and 256 KiB..8 MiB, valid_storage_limits). 0 = not stated: the server
      defaults at creation (storage_config::default_limits, spsync_server
      --max_record_size / --chunk_size), "whatever the storage has" when a client
      states its expectation (modes_match, which also covers the unasserted
      replication mode). Wire: create_storage and response_sequence_number carry
      both limits, peer_heads/push_records carry them with the modes so a replica
      creates its copy with identical limits. Persisted in storage_config (old
      databases get the columns added and the compiled defaults, the same on
      every replica). chain_sync: too_big() on the commit and the foreign path ->
      protocol::errc::record_too_big; the limit is over the authenticated record
      content (chain_block::record_bytes), signature and framing (~ a few KiB)
      come on top. Batching: chain_log::get / get_by_origin take a byte budget
      (chain_sync_config::max_response_bytes, 8 MiB) with an 8 KiB per record
      allowance, always at least one record - clients and peers walk ranges as
      before, they just get shorter batches for large records. Client: comm
      delivers the limits in sequence_info (the sequence request is the per
      connection attach exchange: expected modes out, actual modes + limits back;
      the server id rides there too because that answer is where the engine
      decides about a replica switch). The engine learns them once and persists
      them in the record storage's sync_state next to the cursor owner, so an
      oversized object/user/segment change is refused with
      sync::errc::record_too_big before creating the record - offline and right
      after a restart as well; a later answer with other limits is logged as a
      misconfigured replica, the stored ones win. When the RD12 data endpoints
      join the exchange the packet pair should be renamed to an attach/storage
      info exchange; not worth the churn now.
      Tests: storage "limits are persisted and immutable", chain_sync "record
      size limit and size aware batching" (rejection on both paths and after a
      reopen, 41 x ~3 KB records under a 64 KiB budget fetched in full), engine
      "refuses oversized records" (incl. offline after the limits were learned),
      record_storage "limits persist", s2s replica creation compares the filled
      limits.

- RDS 9  Retention / segment interaction                                       [1d]
      With segments.txt SEG 5 (done 2026-09-01): prune data at segment cut,
      retained live objects keep theirs; server GC by data_id references.

- RDS 10 Replication among data servers                                        [2d]
      Copy count k with hash placement, availability exchange between data
      servers over the s2s link (reduced packet set, no heads), pulls by
      manifest, the all-in-one setup where every replica has both roles
      (distributed phase 4 done 2026-09-04, so this is unblocked).

Ordering: RDS 8 first (done). RDS 1-7 are single-server work with the data role
split in from the start; they unblock file sync (use case 1) and groupchat
attachments. RDS 9 and 10 follow.


Resolved questions (2026-09-07)
-------------------------------

q: inline threshold - keep the metadata path for small payloads (group chat
   messages today), no inline field in the descriptor: one mechanism per size
   class keeps the chain small. Hard bound is max_record_size (RDS 8), the
   advisory application cutoff a fraction of it (~32 KiB). Header padding (RD11)
   gives inline payloads the same size hiding as messages.
q: dedup by content_digest - no server-side dedup: data_id depends on the
   per-data nonce, so two uploads of one file are unrelated to the server by
   construction, which hides that two members share a file (convergent
   encryption would give it away). content_digest stays in the encrypted header
   for the client: a client holding a file with that digest skips the download.
   Local reference counting by data_id (RDS 2). Full content addressing deferred.
q: compression - a reserved flag in the encrypted header, client-side only,
   implementation deferred. If it comes: per chunk (random access survives),
   then pad, then encrypt; most large payloads are media and gain nothing.
q: chunk_size - per storage, immutable creation parameter next to the modes and
   the validity limits (RDS 8), range 256 KiB .. 8 MiB (headroom under the
   16 MiB frame cap); the descriptor still carries it so every data is
   self-describing.
q: transfer scheduling - two datas in flight per connection, a window of 4-8
   chunks each; explicit fetches first, then auto-fetches newest first, uploads
   in commit order; no bandwidth caps in the engine (phase 7 rate limiting);
   resume is free through the manifest exchange (RDS 3, RDS 6).
q: fetch access control - membership is enough; the meaningful later split is
   upload rights versus read, not history versus data; wired to the phase 7
   rights when they exist.
q: per-member quotas - server-local only, attributed by the connection's
   authenticated key id for uploads and by the record signer for chain growth;
   only per-storage limits are advertised to clients; after phase 7 rights.
q: replication of data - not a storage mode: server roles, copy count k as
   server policy, no proxying (RD12, RD13).
