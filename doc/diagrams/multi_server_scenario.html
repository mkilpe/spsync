This is a walk-through of the multi server full scenario test (spsync/engine/test/test_multi_server.cpp): three server replicas, six clients (two per server), exercising every record kind and event and asserting the replicas converge. The record tags below are from one real run of the test.

Topology

Three servers in a chain: server 0 and server 2 are not linked directly, so everything between them must relay through server 1. Two clients sit on each server.

Each server keeps its own record log. A client is synced with the records of the server it is attached to; a server never decrypts (it is content-blind).

Records and events

Kind Meaning

(u) user change

membership + encryption-key delivery (D9 merge)

(d) data change

an application object change (a "message")

(s) segment

a signed checkpoint sealing the history before it

commit

a record created locally by a client on that server

replicate

a record received from a peer server (anti-entropy / push)

Phase 1: a change spreads across the chain

Server 0 commits the first user change; it relays 0 → 1 → 2. Then all three servers commit concurrently and the records cross-fill. Note how server 2 receives server 0’s records from server 1 — the transitive relay through the middle.

Phases 2-5: membership, key rotation, segment

Committed in turn, each draining and asserting convergence:

  • membership — a user change removes a member (re-affirmed later by a rotation).

  • key rotation — a client creates a fresh key and hands it to the members inside the user-change KEM envelope; data committed under the new key stays readable.

  • concurrent rotation — two clients rotate at once, leaving two keys at one key sequence (D9); a record is decrypted by trying each candidate key.

Phase 6: partition and heal

Both links go down, isolating server 1. Each side keeps committing and the replicas diverge (the test asserts this). When the links come back the missing records flow both ways and they converge again.

A client on the isolated server 1 also hops to server 2 during the partition (the 4.5 replica resync): it demotes its records to pending, re-syncs on the new replica under its cursor, and keeps committing there.

Final situation: converged, but observed in different orders (D4)
