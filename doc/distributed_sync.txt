SPSync distributed synchronisation plan
=======================================

Markers as in dev-phases.txt:  + done   * in progress   - todo


Goal
----

Support both sync mode families over multiple servers:

  weak modes   (allow_all, require_special_seen, require_data_add_remove_seen)
               multi-master replication, no consensus, deterministic merge

  strict mode  (require_all_seen)
               per-storage consensus (Raft), one leader per storage, forks prevented

plus server-to-server synchronisation, recovery of lagging/restarted/new servers,
and fork detection with transferable evidence.

Incremental: every milestone is usable on its own and is a prerequisite for the next.
First target is weak mode working end-to-end on one server (M1), then on two servers (M3).


Design decisions
----------------

D1  Servers never decide validity, only order. They cannot decrypt, so the only merge a
    server can do is content-blind (union + deterministic order). Semantic merge is client work.

D2  Clients never mutate committed history. No c2s verb for that will ever be added
    (c2s_types currently has none; keep it that way). Repair happens either
    server-to-server inside the replication protocol, or client-locally over records in
    pending_commit state only. Records in in_sync are immutable on the client.

D3  Strict mode keeps the rigid hash chain: last_seen_block = (seq, hash), parent_hash in
    block hash. Forks are *prevented* by consensus, never repaired.

D4  Weak modes bind references by record tag, not by block position. Sequence numbers are a
    per-server cursor, not part of record identity. Each server linearises the record DAG in
    its own order; merge between servers is a union keyed by tag.

D5  Signing is mandatory for any replicated storage. The signature covers a digest of the
    whole record (sha3-512 over serialised record + gcm tag), not the 128-bit GCM tag.

D6  Every record carries a client-chosen stable operation id (op_id, 128-bit random) inside
    the authenticated part, preserved across rebases. Dedup is by op_id, not only tag.

D7  Server replication metadata (term, origin server, server signature over the assignment)
    lives in an envelope *around* chain_block. chain_block stays client-authored.

D8  record_state::in_sync splits into
      acked    one server accepted it (what in_sync means today)
      in_sync  durable: quorum-committed in strict mode, locally durable in weak mode
    Single server: acked -> in_sync immediately. Higher layers (msg_state) follow.

D9  Merge semantics by record class:
      data changes  commutative; union of both branches, display order by sender_time /
                    creation_time (already inside encrypted payload), not chain index
      user changes  deterministic, fail closed:
                      - removal beats addition for the same user
                      - encryption keys are unioned; highest key_seq is used for new writes
                      - merged access is never a superset of what any single signed
                        user_change granted (no escalation by merging)
                    users_change_mode::delta is mandatory on replicated storages
      segment       treated as special; in weak modes a segment is an advisory checkpoint

D10 Detection halts, never heals, in strict mode (surface to operator/app with evidence).
    In weak modes merge heals; the user sees only "messages arrived".

D11 Post-quantum cryptography for everything from now on (decision 2026-08-21, a selling
    point). Backend: Botan 3 (>= 3.9, BSD-2, C++20 API, std::span, ML-KEM/ML-DSA/SLH-DSA/
    FrodoKEM/Classic McEliece/XMSS/HSS-LMS, own TLS 1.3 with hybrid X25519/ML-KEM-768 on
    by default, RFC 7250 raw public keys and external PSK) - preferred, confirmed by the
    0.0c spike; OpenSSL 3.5 LTS is the fallback. Botan replaces BOTH cryptopp and OpenSSL
    (network's asio::ssl use goes away with Botan's TLS). Algorithms:
      signatures      ML-DSA-65 (FIPS 204) for records, server assignments, certificates
      key wrapping    hybrid X25519 + ML-KEM-768 (FIPS 203) KEM for the group-key envelope
      transport       hybrid KEM key exchange + ML-DSA authentication
      symmetric/hash  AES-256-GCM and SHA3-512 stay (already quantum-adequate)
    Every serialised key, signature, envelope and handshake carries a suite id so
    parameter sets can move (ML-DSA-87 / ML-KEM-1024 for a "high" suite; SLH-DSA as
    the conservative fallback if lattice schemes weaken). No RSA/ECDSA/classic DH
    anywhere in new code; classical primitives appear only inside hybrids.


Known defects found during analysis (fix in phase 0, they block replication)
----------------------------------------------------------------------------

B1  chain_sync ctor restores last_block_ from db but not last_data_add_remove_ /
    last_user_change_or_segment_. After restart both are invalid and
    check_rules_special_seen silently skips enforcement (guarded by is_valid()).
    Hidden today only because storage.cpp hardcodes require_all_seen.
    For replication these cursors must be *derived by replay*, never accumulated.

B2  chain_sync::current_record_ is a mutable member smuggling state from check_rules()
    into set_and_save_block(). Non-deterministic under concurrent/alternative apply paths.

B3  record_storage has no truncation path (no DELETE on the record table). Needed for
    uncommitted-suffix rollback (strict) and for client acked->pending demotion.

B4  sync_engine::update_record throws not_implemented when previous_oid_record_tag is
    non-empty: rebase only works for an object's first change. Any contention on an existing
    object is fatal. Multi-server raises retry rates, so this is a hard prerequisite.

B5  storage.cpp:24 hardcodes chain_sync_config{require_all_seen, only_tag}; the mode is not
    read from the db and not settable at create_storage. (dimensions.txt already says mode
    is chosen at creation and immutable afterwards.)

B6  try_commit_pending: "//t: handle allow_all correctly" - in weak modes it recommits
    without rebasing even when the server demands a special record seen.

B8  (found 2026-08-27 in 1.2) database_record::set_state updates the seq/hash/parent
    columns but not the serialised record blob, so record() of a committed CLIENT record
    returns the predicted sequence and an empty parent hash (server side blobs are
    correct: they are serialised after assignment). Harmless for the engine today
    (authenticated content is unaffected) but must be fixed before clients serve blocks
    to peers (phase 4); until then callers bake in block_id()/parent_block_hash().

B7  Server never verifies signatures (auth_mode only checked structurally on client).
    Server has no private key use at all (only in tests).


Milestones
----------

  M0  securepath library consolidated + modernised; spsync builds on
      it, crypto reworked post-quantum; B1/B2/B5 fixed; per-storage
      mode configurable                    DONE 2026-08-26  (phase 0)
  M1  weak mode works end-to-end, one server, N concurrent clients,
      rebase of existing objects, conflicts surfaced to app   DONE 2026-08-27  (phase 1)
  M2  authenticity hardened: digest signing, op_id, mandatory signing
      on replicated storages, server verifies                           DONE 2026-08-29 (phase 2)
  M3  two servers, weak mode, replication + anti-entropy, client can
      switch server                                                     (phase 3+4)
  M4  server recovery: restart, bootstrap new replica, lag catch-up,
      equivocation evidence                                             (phase 5)
  M5  strict mode on 3-node Raft cluster                               (phase 6)
  M6  ops hardening                                                     (phase 7)

      Current state: RSA for signing, envelope and key ids; custom DH handshake

      HKDF, PBKDF2 via cryptopp. Own certificate format (key/identifier/property

      Keep the public API shape (private_key, public_key, public_key_id, signature,
      enveloped_content, certificate*, auth_stream_cipher, hash, hkdf, random); the
      ~30 call-site symbols outside the lib (116x public_key_id, 35x public_key,
      19x private_key, 15x generate_rsa_private_key, 8x enveloped_content, ...) are
      the compatibility surface. Steps:
        - backend: Botan 3.9 (Fedora: botan3-devel 3.9.0; Android via configure.py
          --os=android for gc_lib). PK_Signer/PK_Verifier for ML-DSA, PK_KEM_Encryptor/
          Decryptor for ML-KEM, AEAD_Mode for AES-256-GCM, SHA-3, HKDF, PBKDF2/Argon2id.
          cryptopp and OpenSSL removed. Known gaps found 2026-08-21 (verify on 3.9):
            . ML-DSA context strings (FIPS 204 ctx) are not exposed -> domain-separate
              in the message instead: sign sha3-512(context || digest)
            . no public hybrid-KEM combiner outside TLS -> own combiner: X25519 KEM +
              ML-KEM-768, shared secret = HKDF-SHA3(ss_x25519 || ss_mlkem || ct_x25519 ||
              ct_mlkem || pk...) following the X-Wing construction; ~100 lines + KATs
            . Botan::TLS::Stream (asio_stream.h) requires Boost.Asio, not standalone
              asio (this code base is standalone asio). Botan::TLS::Client/Server are
              transport-agnostic via TLS::Callbacks, so write a ~300-line stream over
              standalone asio inside network/encryption (fits the existing
              encrypted_connection design). Q10.
            . no FIPS 140 validation (OpenSSL has a FIPS provider); Botan's TLS 1.3 and
              PQC were developed with BSI funding (Rohde & Schwarz Cybersecurity) -
              the assurance story for EU customers; revisit if US-federal FIPS is asked

          encaps/decaps + X25519 combiner, TLS 1.3 client/server over standalone asio
          with raw public keys and X25519/ML-KEM-768. Pass -> Botan; fail -> OpenSSL 3.5.
          + DONE 2026-08-21, Botan 3.9.0 passes: all primitives (ML-DSA-65 sig 3309 B,
            sign 1.8 ms; ML-KEM-768 ct 1088 B; combiner; AES-GCM; SHA3; Argon2id) and
            TLS 1.3 over standalone asio with HYBRID x25519/ML-KEM-768 + mutual raw keys.
            CAVEAT: Botan TLS signs only with RSA/ECDSA (no ML-DSA sigalgs, EdDSA excluded
            upstream) -> the TLS raw key cannot be our ML-DSA key; see Q9 update.
        - suite id: enum crypto::suite { pq1 = ML-DSA-65 + X25519MLKEM768 + AES-256-GCM
          + SHA3-512, pq1_high = ML-DSA-87 + X448MLKEM1024, ... } serialised in every
          key, signature, encrypted_key, certificate and handshake hello
        - keys: private_key/public_key become (suite, sig key, kem key) pairs; a user
          identity = one ML-DSA key + one hybrid KEM key; public_key_id = SHA3-256
          over the serialised public key (both halves)
        - signature: ML-DSA-65 over the message (ML-DSA hashes internally; the record
          digest from 2.1 is the message); context string per use
          ("spsync-record", "spsync-assign", "sp-cert") to stop cross-protocol reuse

          hybrid KEM ciphertext (1088 B ML-KEM-768 + 32 B X25519) + AES-256-GCM-wrapped
          key; decapsulate + unwrap on receive
        - generate_rsa_private_key -> generate_private_key(suite); test contexts
          use pq1 (ML-DSA keygen is fast, RSA-1024 was only ever a test shortcut)

          X25519/ML-KEM-768 key exchange (Botan default), pk variant = RFC 7250 raw

          dh variant (anonymous) dropped. The own certificate model stays above TLS
          (Botan's Credentials_Manager hands out the raw key; our certificate chain is
          checked in the TLS::Callbacks). Q9/Q10 below.
        - sizes: ML-DSA-65 sig 3309 B, pk 1952 B; ML-KEM-768 ct 1088 B, pk 1184 B.
          A signed chat record grows by ~3.4 KB; a user_change for N members by

          agreement later (MLS-style), out of scope here.
        - tests: all 30 crypto tests ported + known-answer tests from the FIPS 203/204
          vectors; [security] bit-flip tests on ML-DSA signatures and KEM ciphertexts;
          interop check of signatures against `openssl pkeyutl`.
        - key/cert migration: nothing deployed, so no RSA compatibility path; the
          suite id exists for future PQ-to-PQ moves, not for RSA.

Open questions (decide before the phase that needs them)
--------------------------------------------------------

Q1 (phase 0.5)  Mode per storage only, or also per record class (e.g. data allow_all,
                users require_special_seen)? The server rules already distinguish the
                classes; exposing it is cheap. Recommend: per storage, with
                require_special_seen as the weak default for chats.

Q2 (phase 2.1)  Drop v0 tag-signed records entirely (nothing deployed) or keep a
                compatibility path? Recommend drop.

Q3 (phase 4.2)  Weak-mode durability definition: local disk of one replica, or
                "pushed to at least one peer" before in_sync? Start with local; revisit
                once 4.4 exists (cheap to switch: delay the acked->in_sync step).

Q4 (phase 4.3)  Change record_base (structure_version 2) or carry last_seen_special_tag
                in trailing_data? Version bump is cleaner; trailing_data keeps old
                clients reading new records. Recommend version bump; no deployment to
                protect yet.

Q5 (phase 6.1)  NuRaft vs own. Decide with a one-day spike: chain_log as NuRaft
                log_store, one storage, three nodes, commit a block.

Q6 (phase 6.2)  Tombstone vs reject for entries that fail validate at apply time.
                Tombstone keeps logs identical and is simpler; costs a log slot.

Q7 (phase 0.0c) Parameter sets: ML-DSA-65 + ML-KEM-768 (NIST level 3) as the default
                suite, or go straight to ML-DSA-87 + ML-KEM-1024 (level 5, what CNSA 2.0
                mandates)? Cost is ~40% larger signatures/keys. Recommend level 3 default
                with the level-5 suite selectable per storage at creation.

Q8 (phase 0.0c) Hybrid for signatures too (composite ML-DSA-65 + Ed25519, IETF LAMPS
                draft) or pure ML-DSA? KEM is hybrid regardless (industry consensus:
                Signal PQXDH, Apple PQ3, TLS X25519MLKEM768). Recommend pure ML-DSA for
                signatures with a composite suite id reserved; revisit if customers ask.

Q9 (phase 0.0c) Transport: own KEM handshake vs TLS 1.3. Recommend TLS 1.3 from Botan
                (reviewed protocol, hybrid PQ group default, RFC 7250 raw public keys for
                the pk variant, external PSK for the ss variant); the own handshake only
                if the spike fails. Either way the hello carries the suite id.
                UPDATE 2026-08-21 (spike): Botan TLS cannot authenticate with ML-DSA, so
                "raw ML-DSA key" is out. Options: (a) Botan TLS 1.3 with an EPHEMERAL
                ECDSA raw key as channel binder + PQ authentication = ML-DSA signature over
                the RFC 5705 exporter (our certificate chain checked there); verified in
                the spike, single backend, Boost-free (recommended). (b) own KEM handshake
                (ML-KEM + ML-DSA-signed transcript). (c) OpenSSL 3.5 TLS (has ML-DSA
                sigalgs + asio::ssl) as a second backend next to Botan. Decision pending.

                DECIDED 2026-08-25: option (a), keeping the escape hatch open — migrate

Rationale summary (from the analysis, kept short)
------------------------------------------------

* chain_sync already is a deterministic state machine over an append-only log; commit
  is compare-and-swap on the head; the client already implements fetch-rebase-retry.
  Consensus goes *under* storage::commit_block, nothing above changes shape.
* Servers never see plaintext, so replicas need to agree on order only. Crash-fault
  consensus is enough for the strict data path; confidentiality holds regardless of
  how many replicas are compromised. Byzantine *ordering* attacks (equivocation) are
  made detectable and provable by client-authenticated back references plus
  server-signed sequence assignments, not by BFT consensus.
* The chain is transitively committed by clients (last_seen_block inside the
  authenticated payload, block hash covers seq + parent). This is the property that
  makes strict mode verifiable without trusting any server - keep it, which is why
  strict mode cannot be re-linearised and must use consensus.
* Weak modes never had a meaningful total order; binding references by tag lets
  every replica linearise its own way and merge by union. Chat lives here.
* Automatic fork recovery is only impossible when ordering is strict *and* there is
  no consensus - which is exactly the single hard-coded configuration today. Both
  exits are automatic: consensus for strict, merge for weak.
