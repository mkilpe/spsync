This is not a REST API but the application's own boundary between the core and a front
end: plain JSON in, plain JSON out, no transport of its own.

=== Commands

A command is a function of `json_manager` called by name. Its argument is one JSON
object (an empty string where the command takes nothing) and its answer is one JSON
value. Commands run on the core's own thread and return when done; two of them,
`create_chat` and `join_chat`, wait for the network first. From the notification
callback a command may not wait for the network: it answers with an error then.

[caption=""]
.The answer of a failed command
[frame=none]
|===
a|
----
{"error": {"code": <integer>, "message": "<the error category's text>", "aux": "<what happened>"}}
----
|===

Every error answer has this shape, whatever the command; a command that succeeded
never has an `error` member. Commands that have nothing to say answer `{}`.

=== Notifications

The core reports through the callback given at construction with a type and a JSON
object. The types are `state_change` (a connection or a chat changed), `request`
(something arrived that a person has to act on) and `notification` (reserved). The
object always has a `type` naming the kind of thing and `data` with the details:

[caption=""]
.notification
[frame=none]
|===
a|
----
{"type": "chat", "data": {"action": "message", "server": 1, "chat": "<chat id>", "message": {...}}}
----
|===

Notifications come from the core's thread; a front end hands them to its own thread
before touching its views.
